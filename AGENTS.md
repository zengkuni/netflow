# Working in this repo

A SOCKS5 proxy for Android that pins outbound traffic to the cellular network.
Project directory is now `netflow/` (renamed from `dataproxy-dev/`); the Gradle
project, Android package, and brand are all `Netflow` / `netflow.dev`.

Latest released version is **v1.3** (versionCode 8; `versionName` is the bare
string `"1.3"`, not `"1.3.0"`). It hardens the data path: stopping the proxy
now force-closes live tunnels, the accept loop survives transient errors, there
is a 512-connection admission cap, auth fails closed when enabled with blank
credentials, the UDP relay only accepts datagrams from its own control peer,
and DNS is resolved by an in-app client (`CellularDnsResolver`) rather than
`Network.getAllByName`.

**No em-dashes anywhere** in app strings, code comments, the README, or release
notes. The user asked for this explicitly; a plain comma, period, or
parenthesis instead.

v1.2 (versionCode 7) added the **Anti-Kill** survival hub (a header chip to a
screen that walks the OEM battery / auto-launch / background-activity /
lock-in-Recents settings), **auto-start on boot**, and fixed the header
carrier name. To allow boot start, `ProxyService`'s foreground type changed
from `dataSync` to `specialUse` (see Architecture invariants).

v1.1.0 (versionCode 6) fixed the long-running "rapid stoptostart leaves proxy
stuck" bug, restored LAN inbound (which v1.0.0 silently broke via
`bindProcessToNetwork`), added a live cellular tech + operator header
indicator, and overhauled the permissions dialog.

## Build & run

The user has Android Studio installed at `/opt/android-studio` (bundled JBR
Java 21) and the SDK at `/home/mmd/apps/Android/sdk` (only `android-36` /
`build-tools 36.x` are present, **do not** drop `compileSdk` back to 35).
There's a downloaded Gradle at `/home/mmd/apps/gradle-8.10.2/bin/gradle`.

```bash
# Release APK (the one shipped to GitHub Releases)
/home/mmd/apps/gradle-8.10.2/bin/gradle :app:assembleRelease \
  --no-daemon --console=plain 2>&1 | grep -E "^(e:|FAIL|BUILD)" | tail -15

# Install on the connected Samsung device
cp app/build/outputs/apk/release/app-release.apk /tmp/Netflow-vX.Y.Z.apk
adb -s R5CY50CMNWM install -r /tmp/Netflow-vX.Y.Z.apk

# Crash check
adb shell am force-stop netflow.dev && adb logcat -c
adb shell monkey -p netflow.dev -c android.intent.category.LAUNCHER 1
adb logcat -d AndroidRuntime:E "*:S" | tail -20

# End-to-end smoke test once the proxy is running (use time.ir, NOT 8.8.8.8 /
# example.com, the user's mtnirancell cellular network blocks those):
curl --socks5-hostname 127.0.0.1:1080 -s -o /dev/null \
  -w 'http=%{http_code} time=%{time_total}s\n' --max-time 25 https://time.ir
```

`org.gradle.java.home=/opt/android-studio/jbr` is set in `gradle.properties`
so command-line builds pick up the JBR automatically (system Java is 26,
which Gradle 8.10 doesn't officially support, it works but warns).

If multiple ADB devices show up (e.g. an emulator + the phone), pass
`-s R5CY50CMNWM`, that's the physical Samsung the user actually tests on.

## Release process

1. Bump `versionCode` + `versionName` in `app/build.gradle.kts`.
2. Bump `app_version` in `res/values/strings.xml`. (The Home footer that used
   to carry a literal version string was removed; `strings.xml` is the only
   place the version shows now.)
3. Bump the release line in `README.md`'s **Pasang** section: both the
   "Rilis terbaru" line and the `Netflow-vX.Y.Z.apk` filename. The README
   is written in Bahasa Indonesia. The release badge is generated by
   shields.io and needs no edit.
4. Build, install, smoke-test on device.
5. Commit, push, then:
   ```bash
   gh release create vX.Y.Z /tmp/Netflow-vX.Y.Z.apk \
     --repo zengkuni-dev/netflow \
     --title "Netflow vX.Y.Z" \
     --notes "..."
   ```

**Every fix, feature, or doc change must be committed and pushed in the same
session.** No waiting for a separate go-ahead, no parking work locally: once
the change is verified (build, device test, or whatever the surface allows),
`git commit` it and `git push origin main` before yielding. `main` is
fast-forward only; if the push is rejected, fetch and reconcile, never
force-push. Commit messages must not include `Co-Authored-By` or any AI
attribution. Build + install locally and hand the APK to the user for device
testing *before* the push whenever the change is user-visible, but the commit
and push still happen in that same session.

**Never bump the version on your own initiative**, not even when adding a
feature, despite step 1–2 above. The user decides when a release is cut and
what the version string is; bump `versionCode` / `versionName` / `app_version`
/ the footer literal *only* when they explicitly tell you to (they pushed back
hard once when a feature build was auto-bumped). Build + install for testing
keeps the existing version, the shared signing key means `adb install -r`
upgrades in place regardless of version code.

The signing keystore is `app/keystore/netflow-release.jks` (gitignored,
password `netflow`). Same key has been used for every release, installs
upgrade in place. If the keystore file is missing, the build still succeeds
with an unsigned APK (signing config is conditional in `build.gradle.kts`).

## Architecture invariants

These are load-bearing, break them and the app stops working.

- **Never call `cm.bindProcessToNetwork(cellular)`.** It tags every socket
  the process creates, including the SOCKS5 listener, with the cellular
  netId. The kernel then routes the listener's SYN-ACK reply via the
  cellular route table, so external clients on Wi-Fi never finish the TCP
  handshake (SYN_RECV to retransmits to timeout). v0.2.1 to v1.0.0 had this
  bug; v1.1.0 removed all `bindProcessToNetwork` calls. The "DNS leak"
  rationale was theoretical only, every hostname resolution in this app
  goes through `Network.getAllByName()` via `cellular.resolveHost()`, and
  there is no `URL` / `OkHttp` / `HttpClient` anywhere on the data path.
- **Domain DNS goes through `Network.getAllByName`.** In `Socks5Connection
  .openRemote`, hostnames are resolved via `cellular.resolveHost(host)` -
  this is now the *only* DNS path, not belt-and-suspenders. If you ever
  add a code path that calls `InetAddress.getByName(hostname)` you've
  introduced a leak.
- **`CellularNetworkProvider` is a lazy singleton on `ProxyService`** (`val
  cellular by lazy { ... }`). It is *not* recreated per start/stop cycle.
  An attempt to make it per-cycle (during the v1.0.0 stale-state-after-
  `adb install -r` investigation) regressed rapid power-toggle: building a
  *new* `NetworkCallback` object every cycle exposes a race in
  `ConnectivityManager.unregisterNetworkCallback` to `requestNetwork` when
  the second call lands a few ms after the first. The same callback object
  re-registered is fine. **Don't reintroduce per-cycle recreation.**
- **`fullCleanup()` is called on BOTH start and stop.** `ProxyService` has
  a single helper that cancels every job (including the `startJob` that
  wraps `awaitAvailable`), stops the server, calls `cellular.stop()`,
  resets the registry/sampler, and releases the wake lock. It runs at the
  top of `startProxy` *before* `cellular.start()` and again inside
  `stopProxy`. Without the start-side call, a leftover `awaitAvailable`
  watcher from a partially-aborted previous cycle could fire `onAvailable`
  after the new launch had already built a `Socks5Server`, racing them on
  port 1080; the loser's `onFatal` called `cellular.stop()` and killed
  the winner's network handle. That was the "force-stop is the only cure"
  rapid-toggle bug; **the fix relies on `fullCleanup()` being idempotent
  and called from both sides, don't shortcut it.**
- **`startProxy`'s launch is tracked as `startJob`.** It's no longer a
  fire-and-forget `scope.launch { ... }`. The cancellation flows into
  `awaitAvailable`'s `invokeOnCancellation` which unregisters its private
  watcher `NetworkCallback`. Without the tracking the watcher leaked
  across stoptostart cycles.
- **`ProxyService` is a `specialUse` foreground service, not `dataSync`.**
  Android 15+ refuses to start a `dataSync` FGS from a `BOOT_COMPLETED`
  receiver (`ForegroundServiceStartNotAllowedException`; the blocked set is
  dataSync / camera / mediaPlayback / phoneCall / mediaProjection /
  microphone), which would break auto-start-on-boot. `specialUse` is exempt.
  The manifest declares `FOREGROUND_SERVICE_SPECIAL_USE` + the
  `PROPERTY_SPECIAL_USE_FGS_SUBTYPE` property, and `startForegroundNow`
  passes `FOREGROUND_SERVICE_TYPE_SPECIAL_USE`. **Don't switch back to
  `dataSync`**, boot start breaks. (Google Play would gate `specialUse` at
  review, but Netflow ships via GitHub Releases, so runtime is unaffected -
  same choice as the xsms `KeepAliveService`.)
- **`ProxyService.State.Paused` is not Stopped.** When cellular drops, the
  service stays in the foreground and the listener stays bound. New outbound
  connects just fail with `REP_NETWORK_UNREACHABLE`. When cellular comes
  back, the watcher coroutine flips back to `Running`.
- **`State.Error(ErrorKind)` drives UI dialogs.** `ErrorKind
  .MobileDataUnavailable` is what makes `MainActivity` show the "mobile data
  is off" dialog. Don't collapse the kind enum into a bare message string.
- **`cellularState` is a computed property** (`get() = cellular.state`),
  not a `val =`. The `cellular by lazy { CellularNetworkProvider
  (applicationContext) }` block touches `applicationContext`, which is null
  during `ProxyService.<init>`, eagerly reading the lazy crashes the
  service. Verified by a prior NPE; don't undo it.
- **`cellular.awaitAvailable` timeout is 15 s** in `ProxyService.startProxy`.
  6 s was the original value; cold cellular activation on the user's
  Samsung / mtnirancell SIM regularly takes 8–12 s (acquire radio to PDP
  context to IP to validate), so 6 s was firing prematurely on the *first*
  start after a reboot or fresh install. Don't lower it.
- **No `cm.allNetworks` pre-check for mobile data.** Samsung's OneUI hides
  the cellular network from `allNetworks` when Wi-Fi is the active default,
  which made the v0.2 pre-check return false positives. v1.1.0 *does* use a
  fast pre-start check, but via `TelephonyManager.isDataEnabled()` (a
  user-toggleable setting, not a routing table snapshot) read by
  `CellularTechMonitor`. The 15 s `requestNetwork` timeout in
  `ProxyService.startProxy` is still the source of truth for the
  `MobileDataUnavailable` error state.
- **DNS resolver cache is disabled JVM-wide** in
  `NetflowApplication.onCreate` via
  `Security.setProperty("networkaddress.cache.ttl", "0")` (+ negative).
  Cellular carriers in censorship regions periodically serve hijacked DNS;
  caching a poisoned answer until next force-stop would silently break TLS
  for the affected host until then.
- **Failed outbound TCP handshakes RST instead of FIN.** In
  `Socks5Connection.openRemote`'s `catch (IOException)`, the outbound socket
  is closed with `setSoLinger(true, 0)` so the carrier NAT entry for the
  failed 5-tuple is dropped immediately rather than lingering in `TIME_WAIT`.
- **`CellularTechMonitor` polls TelephonyManager every 2 s.** All calls are
  `runCatching`-wrapped so a missing permission or pre-API anomaly can't
  crash anything, the worst case is `TechState.Unknown`. The header
  consumes its `StateFlow` and is the only screen that uses it. Don't
  swap to a `TelephonyCallback`-based push API on pre-31 devices unless
  you also keep the polling path; the API didn't exist until S.
- **The tech monitor reads the *data* subscription, and prefers the SIM
  carrier name.** As of v1.2 it binds to
  `tm.createForSubscriptionId(SubscriptionManager.getDefaultDataSubscriptionId())`
  and reads `simOperatorName` first, falling back to `networkOperatorName`
  only when that's blank. Reading `networkOperatorName` off the *default*
  TelephonyManager made the header carrier name occasionally wrong: the
  registered-network name flickers blank/transient during re-registration,
  and on dual-SIM the system-default sub is often the *voice* SIM. **Don't go
  back to `networkOperatorName` on the default TM.**

## DNS (v1.3)

- **`CellularDnsResolver` is the only resolver on the data path.** It sends A
  and AAAA queries itself, over a `DatagramSocket` bound to the cellular
  `Network`, to the servers in that network's `LinkProperties`. There is no
  configurable resolver and no fallback to the platform one; the single
  fallback is `Network.getAllByName` (still cellular-pinned) when the link
  advertises no DNS servers at all.
- **Why not `Network.getAllByName` alone.** On an IPv4-only APN Android
  suppresses AAAA entirely, so an IPv6-only host fails at the *resolve* step.
  Clients told "cannot resolve" tend to re-resolve the name themselves, off
  network. Resolving in-app means the lookup succeeds and the failure lands at
  connect, reported as `REP_NETWORK_UNREACHABLE` via `hasIpv6()`.
- **Never pass a hostname to `InetAddress.getByName`.** That is the system
  resolver on the default network, i.e. Wi-Fi. `parseLiteral` guards it with a
  strict IPv4 regex plus a colon test. An earlier version used "starts with a
  digit", which sent `9gag.com` and similar straight out over Wi-Fi.
- **`openRemote` tries every resolved address**, not just the first. A
  censoring carrier routinely returns one blackholed address alongside working
  ones.
- **Known limitation:** the carrier APN here is IPv4-only, so IPv6 destinations
  cannot be proxied at all, and a client that asks for one will resolve it
  itself. A SOCKS5 proxy cannot prevent that; only a VpnService could.

## SOCKS5 protocol surface (v1.1)

- **CONNECT (0x01)**: TCP tunnel, the original feature. Hostname ATYP
  resolves via cellular DNS as above.
- **UDP ASSOCIATE (0x03)**: `Socks5UdpRelay` opens two `DatagramSocket`s,
  a client-side one bound to the same address the TCP control arrived on,
  and a remote-side one bound to cellular via
  `CellularNetworkProvider.createBoundDatagramSocket()`. SOCKS5 UDP
  headers (RFC 1928 §7, `RSV(2) + FRAG(1) + ATYP + DST + DATA`) are parsed
  on ingress and re-emitted on egress. `FRAG != 0` is rejected (no
  fragmentation support, matches every common UDP client). The relay
  shuts down when the TCP control closes.
- **BIND (0x02)**: not implemented; returns `REP_COMMAND_NOT_SUPPORTED`.
- **Auth (RFC 1929)**: toggleable per-Auth-screen prefs (`auth_enabled`,
  `auth_username`, `auth_password` in `netflow_prefs`). Read live by
  `ProxyService.currentAuthConfig()` on each new connection so toggling
  doesn't need a proxy restart. When disabled, only method 0x00 (no-auth)
  is offered; when enabled, only 0x02 (user/pass).

## Permissions flow (v1.1)

Triggered only when the user taps the power button, never at launch. v1.1
**dropped the auto-chain** in favour of per-item *Allow* buttons inside the
dialog; the user explicitly clicks each one and the system prompt fires
only for that single permission.

1. `MainActivity.onPowerToggle` is the gatekeeper:
   - If `viewModel.cellularTech.value is TechState.DataOff` to show the
     `MobileDataDialog` (with "Open settings") and bail. This is the
     *pre-start* mobile-data check, it intercepts before the 15 s
     `requestNetwork` ever runs. The old behaviour (let the service start,
     fail, and surface the error 15 s later) is still the safety net via
     the `serviceState` `LaunchedEffect`.
   - If any of `needsNotifPermission()`, `!BatteryOptimizationHelper
     .isIgnoring()`, or `needsPhonePermission()` (pre-33 only) is true to
     show `PermissionsDialog` with `permsDialogStartsProxy = true`.
   - Otherwise to `actuallyStart()`.
2. `PermissionsDialog` (in `AppNav.kt`) always shows the items applicable
   to this Android version with a per-item state:
   - granted to green `CheckCircle` icon
   - not granted to `Allow` text button that invokes the matching launcher
     (`requestNotifPermission`, `requestBatteryOptIgnore`,
     `requestPhonePermission`)
   - the polling `LaunchedEffect` recomputes `*Granted` booleans every
     1.5 s, so the dialog updates without any extra signalling
3. The dialog's bottom button is **always `Done`**, there is no `Cancel`.
   On dismiss, if `permsDialogStartsProxy` was true,
   `actuallyStart()` runs regardless of grant state (declined perms are
   allowed; the proxy still works, only foreground/survival degrade).
4. The header's network-indicator click opens the same dialog with
   `permsDialogStartsProxy = false`, granting the optional pre-33 phone
   perm without starting the proxy.

**`READ_BASIC_PHONE_STATE` is auto-granted on API 33+** (normal install-time
permission); declared in the manifest with no prompt path. The pre-33
fallback is `READ_PHONE_STATE` with `android:maxSdkVersion="32"` so modern
users never see it in the dialog. The runtime check
`needsPhonePermission()` already encodes this, returns `false` on API 33+.

**Don't reintroduce the auto-chain.** It was originally there to walk one
system prompt at a time, but the per-item button design supersedes it and
is what the user explicitly asked for. The Android-13+ "auto-deny after
two denies" ANR loop is a non-issue here because each launcher is fired
by a discrete user tap, not from inside an activity-result callback.

Decline is fine for any of them, the service still runs; only the
foreground notification visibility / background survival / header tech
label degrade.

**(v1.2) The same dialog also lists the Anti-Kill OEM steps**, auto-launch,
background activity, lock in Recents, under a "SURVIVE BACKGROUND LIMITS"
subheader (the user asked for the anti-kill prompts to live here too). Those
rows show an "Open" button that opens the OEM settings *and* optimistically
marks the step done via `AntiKillPreferences`; `MainActivity` polls those
flags every 1.5 s. They do **not** gate the start, only Notifications +
Battery do. See the Anti-Kill section.

## Geo-IP card (public IP lookup)

`geo/GeoIpClient.kt` + `GeoCard` di Home menampilkan IP publik, negara, dan
ISP. Permintaan dijalankan di atas jaringan **seluler** (bukan WiFi) lewat
`ConnectivityManager.requestNetwork` dengan `TRANSPORT_CELLULAR`, jadi yang
terbaca IP seluler perangkat.

- **Pool 10 endpoint** (`ipapi.co`, `ipwho.is`, `api.ip.sb`, `ipinfo.io` +
  3 token, `api.getmyip.pro`, `free.freeipapi.com`, `hackmyip.com`), diputar
  **round-robin**; endpoint yang gagal (termasuk 429) masuk cooldown 90 detik
  sehingga tidak dibentrok berulang. Semua endpoint terverifikasi hidup di
  device (http=200, IP publik sama). `api.country.is` sengaja tidak dipakai
  (hanya kirim `{ip, country}`, tanpa ISP).
- **Parser toleran bentuk**: `country` berarti kode 2 huruf di ipapi/ipinfo
  tapi nama negara di ipwho.is/ip.sb, dibedakan dari panjang; nama negara
  fallback ke `Locale` saat provider hanya kirim kode; objek bersarang
  (`data.location`, `data.network` di hackmyip) diratakan; prefix `AS<nomor>`
  dibuang dari ISP agar konsisten antar provider.
- **Trigger**: setiap proxy masuk state `Running` (momen IP seluler bisa
  berubah) dan tap kartu untuk menarik dari provider berikutnya. Kegagalan
  pool tidak memengaruhi apa pun.
- Kode negara 2 huruf dirender sebagai emoji bendera (`flagEmoji`).

## JSON-RPC API (APN/IP control)

Ported from the netflow-go core into `netflow.dev.apn.*` (11 files:
`model/`, `parse/`, `shell/`, `api/`, `jsonrpc/`). Gives the app an APN and
IP-rotation control surface on top of the root shell.

- **Odin was removed.** The upstream core used `com.trinadhthatakula:odin`;
  the port runs on the app's existing libsu seam. `apn/shell/ShellExecutor.kt`
  keeps the upstream interface, and `LibsuShellExecutor` implements it over
  `netflow.dev.util.LibsuRootShell` (never-throws, one persistent root shell
  per process, grant remembered by the superuser manager).
- **`service/JsonRpcService.kt`** hosts `apn/jsonrpc/JsonRpcServer` on
  **0.0.0.0:9060** (bind ke semua antarmuka atas permintaan operator, supaya
  API bisa dipanggil dari host/LAN; method-nya menjalankan perintah root dan
  API tidak berautentikasi, jadi keputusan ini hanya aman di jaringan
  tepercaya, lihat komentar di `JsonRpcService.BIND_HOST`). It is a plain
  (non-foreground) service with **no notification of its own**: one
  notification covers both, `ProxyService.buildNotification` shows
  the proxy endpoint and `API 9060` in a single shade. Started by
  `ProxyService.startProxy` (via `startService`, safe because the proxy is
  already foreground) and stopped by `ProxyService.fullCleanup`, so the API
  lives and dies with the proxy. A failed bind logs and stops the service;
  it never takes the proxy down with it. The legacy `netflow.jsonrpc`
  channel from the two-notification era is deleted in
  `NetflowApplication.onCreate` (channels survive app updates).
- **Transport accepts two shapes on the same port**, detected from the first
  bytes: HTTP/1.1 POST (`curl -X POST`) and newline-delimited JSON
  (`nc 127.0.0.1 9060`). Verified on device: `apn.list` returns the real
  carrier table through the root shell in both modes.
- **Method namespace**: `apn.*` (list / add / current / preferred / delete)
  from `registerApnMethods`, and `auto.changeip.at` /
  `auto.changeip.airplane` from `registerIpMethods`. Every handler returns
  `{ok, error, data}`; failures are result objects, never exceptions, so one
  bad request cannot kill the transport.
- **Safety**: the ported command builders keep the upstream guards
  (`isSafeWhere`, `quoteShellArg`, `sanitizeNumeric`); combined with the
  loopback bind, nothing reachable from the network can reach a shell
  command. Airplane-mode methods were NOT exercised on the user's daily
  device by design.

## Anti-Kill & auto-start (v1.2)

Netflow has a single foreground service (the proxy itself), there is **no**
separate keep-alive service or WorkManager watchdog (unlike xsms). "Anti-Kill"
is a settings-guidance hub plus a boot-restore toggle, not another process.

- **Entry point is the `🛡 Anti-Kill` header chip** (see UI conventions), which
  opens `Tab.AntiKill` to `AntiKillScreen`.
- **`AntiKillScreen`** (`ui/screens/`, a `BackHandler` subscreen): a
  "What is this?" explainer (help icon in the `TopBar`), a progress hero, a
  **Start after reboot** toggle card, and five expandable step cards.
  Notifications + battery are auto-detected (live check); Auto-launch /
  Background activity / Lock in Recents are manual OEM steps (an "Open
  settings" button + an "I've done this" switch).
- **`OemHelper`** (`util/`) detects the manufacturer and deep-links to the
  per-vendor auto-start / background / battery / notification / recents
  screens, falling back to App-details when the vendor activity isn't
  resolvable. The manifest `<queries>` block lists the vendor packages so
  `resolveActivity` works under Android 11+ package visibility, keep it in
  sync with `OemHelper`.
- **`AntiKillPreferences`** (`util/`) stores `autostart_on_boot` and the
  manual `antikill_step_<Name>` flags in `netflow_prefs`. Auto-detectable
  steps are read live, never persisted.
- **`BootReceiver`** (`service/`): on `BOOT_COMPLETED` / `QUICKBOOT_POWERON` /
  `MY_PACKAGE_REPLACED`, if `autoStartOnBoot` is on, it
  `startForegroundService(ProxyService.startIntent(addr, port))` reading the
  saved bind address/port. Semantics: toggle ON = start the proxy on **every**
  boot, not "restore last running state". Relies on the `specialUse` FGS type
  (see invariant), `dataSync` would throw here on Android 15+.
- `MainViewModel.autoStartOnBoot` (StateFlow) + `setAutoStartOnBoot` back the
  toggle; the bind/port pref keys were centralized onto `ProxyService`
  (`PREF_BIND_ADDRESS` / `PREF_PORT`) so `BootReceiver` can read them.

## Fixed in v1.2 (don't undo)

- **Header carrier name is now accurate.** It was occasionally wrong/blank;
  `CellularTechMonitor` read `networkOperatorName` off the default
  subscription's TelephonyManager. Fix: bind to the *data* subscription and
  prefer `simOperatorName`. See the `CellularTechMonitor` invariant.
- **Auto-start-on-boot works** because the FGS type is now `specialUse`. See
  the `ProxyService is a specialUse foreground service` invariant, don't
  revert it.

## Fixed in v1.1.0 (don't undo)

- **Rapid stop to start no longer hangs the proxy.** Root cause was the
  `scope.launch { ... awaitAvailable ... }` in `startProxy` being
  fire-and-forget: `stopProxy` never cancelled it, so its private watcher
  `NetworkCallback` stayed registered, fired `onAvailable` on the next
  cellular event, and resumed into a *second* `Socks5Server` that fought
  the new one for port 1080. The loser's `onFatal` called `cellular.stop()`
  and killed the winner's network handle. Fix: track the launch as
  `startJob` and call `fullCleanup()` at the top of both `startProxy`
  and `stopProxy`. Verified at 50/50 over LAN with no failures.
- **LAN inbound now works.** v0.2.1 to v1.0.0's
  `cm.bindProcessToNetwork(cellular)` was tagging the listener socket
  with the cellular netId, so the kernel routed SYN-ACK out the cellular
  interface instead of `wlan0` and external clients timed out at
  `SYN_RECV`. Removing the call restored normal Wi-Fi inbound; the
  cellular pinning still works because every outbound socket is
  individually bound via `Network.bindSocket()`.

## Root features (v1.3-dev, opt-in)

Root support is additive and off by default (`root_enabled` in
`netflow_prefs`). The app is fully functional without it.

- **B1 (silent Anti-Kill enforcement)**: `util/AntiKillEnforcer.kt` applies the
  generic restrictions from `ProxyService.enforceAntiKillIfRooted()` (called
  right after `startForegroundNow`): POST_NOTIFICATION (appops or
  `pm grant` on TIRAMISU+), `cmd deviceidle whitelist +$pkg`,
  `cmd appops set $pkg RUN_ANY_IN_BACKGROUND allow`,
  `cmd netpolicy add restrict-background-whitelist $uid` (best-effort). It
  re-requests root when `LibsuRootShell.state` is `Unknown` (fresh process
  from the daemon or boot); the superuser manager remembers the grant, so the
  prompt only ever appears for a user who flipped the toggle. OEM autostart /
  lock-in-Recents stay manual guidance, there is no command surface for them.
- **B3 (root watchdog daemon)**: `util/RootDaemon.kt` installs
  `/data/adb/service.d/99netflow.sh` (KernelSU/Magisk boot script) that
  restarts the foreground service whenever the app process is gone. The script
  only acts when `util/WatchdogState`'s marker file (app cache, root-readable)
  says `run`, which the service writes on successful start and clears on
  intentional stop and every error path. Without that gate the daemon cannot
  tell an OEM kill from the user tapping the power button off, and would
  restart a proxy the user just stopped (or restart-loop on a bind error).
  `install()` also starts the loop immediately with
  `setsid nohup sh $SCRIPT &` (service.d only runs at boot, so a plain
  install would be inert until reboot); a pgrep guard prevents duplicate
  loops. `uninstall()` uses `pkill -f 99datap[r]oxy.sh` (bracket form: the
  transient exec shell's own cmdline would otherwise self-match).
- **Never interpolate untrusted input into `Shell.cmd(...)`.** All commands are
  static strings with `BuildConfig.APPLICATION_ID`, `applicationInfo.uid`, and
  app-owned cache paths substituted; nothing from the network or a SOCKS5
  client ever reaches a shell command.
- **Root features never block or fail proxy start.** Every root call is
  `runCatching`-wrapped; a denied or unavailable root degrades to the manual
  guidance path.
- **libsu core 6.0.0** (jitpack) with the ~20-line suspend shim in
  `util/LibsuRootShell.kt`; no libsu-extensions, no Odin.
- **Verified on Xiaomi Redmi Note 5 (LineageOS 18.1, KernelSU, serial
  5d386ae2)**: silent enforcement of all four items from a clean slate;
  daemon restart after force-stop and after reboot; stop-gate; install and
  uninstall via the UI toggle. The TIRAMISU+ `pm grant` branch is untested
  (no Android 13+ rooted device).

## Things that broke during early development (don't re-introduce)

- `byteArrayOf(0x05, 0x00)` fails to compile, `0x05` is `Int`, `byteArrayOf`
  needs `Byte`. Every byte literal needs `.toByte()`.
- `var x by animateFloat(...)` needs `import androidx.compose.runtime
  .getValue`, `animateFloat` returns `State<Float>`, which has `getValue`
  only as an extension.
- `suspendCancellableCoroutine { cont -> ... cont.resume(null) }` infers
  `T = Network` and rejects `null`. Type the call explicitly:
  `suspendCancellableCoroutine<Network?> { ... }`.
- `material3.ripple` doesn't exist in Compose BOM 2024.11.00, use the
  default ripple from `Modifier.clickable(onClick = ...)`.
- `LocalDPColors`/`Ink`-as-`@Composable get()` is the right pattern, but
  *don't* try to use those getters inside top-level `darkColorScheme(...)`
  initialisers, those run at class init, not in a Composable scope. Resolve
  the DPColors instance inside the `NetflowTheme` Composable and pass its
  fields into `darkColorScheme()` / `lightColorScheme()` there.

  filtered on cellular even though it worked on Wi-Fi. Plain `--socks5`
  failures look like "proxy is broken" but aren't.

## Where scratch files go

**Test scripts, throwaway probes, build logs and any other scaffolding go in
`tests/` at the repo root, never in the repo root itself.** The root has
accumulated 56 `build-*.txt` log dumps over the project's history and they had
to be swept out by hand; `tests/` is gitignored so the same thing cannot happen
again.

Rules:

- Create `tests/` if it is missing. Put every one-off script (`*.py`, `*.sh`,
  `*.ps1`), every captured build log, every device screenshot or `uiautomator`
  dump there, not at the root.
- Keep the project's own test suite where the Gradle module expects it
  (`app/src/test`, `app/src/androidTest`); `tests/` is only for scratch work,
  not for committed unit tests.
- Nothing under `tests/` is read by the build, nor committed. If a scratch file
  turns out to be worth keeping, move it into the tree as a real file and say so
  in the commit; do not leave it in `tests/` and point at it.
- Clean up before handing work over: a `tests/` full of stale logs from three
  tasks ago is the failure this rule exists to prevent.
